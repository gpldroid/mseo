## 2. Recommended direction from the seven design references

Use a hybrid, not a copy:
1. Ahrefs-style direct access to useful tools and actionable SEO workflow.
2. Semrush-style task-based tool taxonomy.
3. Backlinko-style practical guides and scannable article structure.
4. Moz-style learning paths and glossary-like education.
5. HubSpot-style clear content categories and conversion paths.
6. Search Engine Journal-style editorial/news discovery.
7. Exploding Topics-style topic discovery and content ideation.

Preserve the current site's Fast Seo brand and existing visual system. The recommendations above concern information architecture and discovery patterns, not copying another site's visual assets or code.

## 3. Top-level information architecture

- Home: core value proposition; prominent search; shortcuts to tools, SEO, web development, performance, programming and AI; curated latest articles.
- Tools directory: browse tools by job-to-do, with direct links to each current tool page and one-sentence purpose.
- Topics/categories: crawlable category landing pages that link directly to the relevant articles and tools.
- Article archive: searchable, filterable index of published articles; ensure important links are present as ordinary HTML anchors, not only generated by JavaScript.
- Guide pages: educational clusters linking to relevant tool pages, supporting guides and the parent category.
- Individual tools: retain current functionality, add contextually relevant guides and sibling tools without making the actual tool harder to reach.
- About/contact/privacy/terms/editorial policy: keep current legal and trust pages reachable from shared navigation/footer.

## 5. Internal linking rules

1. Add links only where a reader would reasonably want the next step. Prefer links inside relevant paragraphs plus a small “Related guides/tools” section.
2. Use descriptive anchors, such as “دليل الروابط الداخلية” or “مولّد Schema markup”, not repeated generic anchors such as “اضغط هنا”.
3. Each important guide should link upward to its category and sideways to 2–5 closely related pages. Each tool should link to a guide explaining the task and to 1–3 related tools.
4. Category pages should link directly to the actual article URLs, not only rely on client-side search or carousel widgets.
5. Avoid sitewide blocks with dozens of exact-match anchors. Avoid reciprocal links when they provide no value.
6. Do not create synthetic URLs or rename paths until redirects/canonical URLs/sitemap are planned and verified.
7. Keep external links to genuine authoritative resources and mark sponsored/affiliate links appropriately if present.
8. For each page, use one distinct title and meta description, preserve a single canonical URL, and avoid keyword stuffing.
9. Keep Arabic RTL layout intact; for English content, use the page's actual language setting and suitable direction.
10. Measure orphan pages and internal-link counts through the site audit before and after changes.

## 6. Recommended implementation phases

- Phase A — inventory: enumerate every public HTML file, category, tool, canonical and sitemap URL; compare generated catalogs with files actually present.
- Phase B — keyword mapping: record primary intent and secondary terms for every important page; flag competing pages targeting the same intent.
- Phase C — contextual linking: update only article/tool/category content where there is clear relevance; prefer small, reviewable batches.
- Phase D — navigation/discovery: improve category/tool discovery and crawlable links without replacing existing search or carousel behavior.
- Phase E — technical validation: run existing scripts where compatible, including `scripts/audit-seo.mjs`, `scripts/audit-assets.mjs`, `scripts/audit-translations.mjs`, `scripts/check-javascript.mjs`, `scripts/validate-site.mjs`, and regenerate sitemap/RSS only if input catalog conventions are confirmed.
- Phase F — review and deploy: inspect diffs, confirm the custom domain and existing verification files are preserved, run tests on a preview branch, then merge only after the checks pass.

## 7. Release checklist

- [ ] Every internal link resolves to an existing file.
- [ ] Every public HTML page has a unique title, meta description and canonical URL.
- [ ] Canonical URLs and `og:url` match the production domain and the real page URL.
- [ ] `robots.txt` points to the correct sitemap.
- [ ] Sitemap contains all intended public pages and no broken/retired URLs.
- [ ] Current tools still function with empty, valid, invalid and edge-case inputs.
- [ ] Desktop/mobile layout and keyboard navigation remain usable.
- [ ] Arabic RTL and bilingual language behavior are preserved.
- [ ] GitHub Pages / custom domain deployment remains intact.
- [ ] No new page is published before its URL, keyword target and related-link set are confirmed.

## 8. Execution boundary

This plan is intentionally separate from live page edits. The repository has existing content, tool-specific scripts and metadata; changing many files in one pass without first running the actual site validators could create regressions. Use this document as the implementation checklist and update individual pages in small batches, comparing each change against the validation scripts before merging.
