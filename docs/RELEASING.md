# سياسة الإصدارات والتغييرات

تعتمد FastSEO سياسة واضحة لتوثيق التطوير وإصدار النسخ، مع الحفاظ على GitHub Pages كمنصة النشر الوحيدة.

## 1. ترقيم الإصدارات

يُستخدم ترقيم Semantic Versioning بالشكل:

`MAJOR.MINOR.PATCH`، وتُسبق وسوم Git بالحرف `v` مثل `v1.2.3`.

- **MAJOR:** تغيير غير متوافق مع الروابط أو البيانات أو الواجهات أو طريقة تشغيل المشروع.
- **MINOR:** إضافة وظيفة جديدة متوافقة مع السلوك والروابط الحالية.
- **PATCH:** إصلاح خطأ أو تحسين صغير لا يكسر التوافق.
- **Pre-release:** عند الحاجة للاختبار العام، استخدم لاحقة مثل `v1.3.0-rc.1`.

يظل المشروع ضمن سلسلة `0.x` إلى أن يُعلن عن أول إصدار مستقر. قبل `1.0.0)، يمكن أن تتضمن زيادة MINOR تغييرات غير متوافقة؛ ويجب توضيحها في سجل التغييرات. لا تنشئ وسم إصدار لمجرد دمج Pull Request؛ الإصدار الرسمي يحتاج قراراً صريحاً وتجهيزاً واختباراً.

## 2. تحديث CHANGELOG.md

يجب تحديث `CHANGELOG.md` في كل Pull Request يتضمن تغييراً ذا أثر على المستخدم أو المحتوى أو SEO أو الروابط أو التصميم أو البناء أو النشر.

استخدم الأقسام التالية عند الحاجة:

- **Added:** ميزات جديدة.
- **Changed:** تغييرات السلوك أو التصميم.
- **Deprecated:** ميزات معلن عن إيقافها لاحقاً.
- **Removed:** ميزات أو ملفات أزيلت.
- **Fixed:** إصلاحات.
- **Security:** إصلاحات أو تحديثات أمنية.

قواعد الكتابة:

1. اكتب وصفاً واضحاً موجهاً للمستخدم أو المطور، لا مجرد اسم commit.
2. اذكر التأثير المهم، مثل تغيير رابط أو متطلب بناء أو إعداد نشر.
3. لا تسجل تفاصيل داخلية غير مؤثرة ولا تغييرات لم تُدمج.
4. أضف البنود الجديدة تحت `[غير مُصدر] - Unreleased` في أعلى الملف.
5. عند الإصدار، انقل البنود المكتملة إلى عنوان الإصدار مع التاريخ بصيغة `YYYY-MM-DD`.
6. رتّب الإصدارات من الأحدث إلى الأقدم، ولا تعدّل سجل إصدار منشور إلا لتصحيح معلومة موثقة.

## 3. نمط رسائل الالتزام

استخدم Conventional Commits:

`type(scope): short imperative summary`

الأنواع الموصى بها:

| النوع | الاستخدام |
|---|---|
| `feat` | ميزة جديدة |
| `fix` | إصلاح خلل |
| `docs` | توثيق فقط |
| `style` | تنسيق لا يغير السلوك |
| `refactor` | إعادة تنظيم دون تغيير الوظيفة |
| `perf` | تحسين الأداء |
| `test` | اختبارات |
| `build` | أدوات واعتماديات البناء |
| `ci` | GitHub Actions وسير CI |
| `chore` | صيانة عامة |
| `revert` | التراجع عن تغيير سابق |

أمثلة:

```text
feat(search): improve article and category search
fix(articles): restore category archive cards
docs(changelog): record release changes
build(hugo): update extended build workflow
ci(pages): verify deployment artifact
```

إذا كان التغيير يكسر التوافق، أضف `!` بعد النوع أو اكتب تذييل `BREAKING CHANGE:` واشرح أثره وخطوات الترحيل.

## 4. قواعد Pull Request

كل Pull Request يجب أن:

1. يشرح المشكلة والنتيجة المطلوبة.
2. يحدد الملفات أو المكونات المتأثرة.
3. يحدّث CHANGELOG.md عند وجود تغيير مؤثر.
4. يوضح الاختبارات التي نُفذت ونتائجها، وأي اختبار لم يُنفذ.
5. يحافظ على روابط المقالات والتصنيفات ما لم يكن تغييرها مقصوداً وموثقاً.
6. لا يخلط إعادة تصميم واسعة مع إصلاح صغير دون ضرورة.
7. لا يضيف أسراراً أو مفاتيح وصول إلى المستودع.

## 5. قائمة إصدار نسخة

قبل إنشاء إصدار رسمي:

- [ ] مراجعة جميع Pull Requests المدمجة منذ الإصدار السابق.
- [ ] نقل البنود المكتملة من Unreleased إلى عنوان الإصدار الجديد في CHANGELOG.md.
- [ ] تحديد رقم MAJOR أو MINOR أو PATCH وفق SemVer.
- [ ] تشغيل `npm install` ثم `npm run build`.
- [ ] مراجعة مخرجات Hugo وفهرس البحث وأرشيفات التصنيفات والروابط وSEO.
- [ ] التأكد من نجاح GitHub Actions.
- [ ] التحقق من الموقع المنشور على GitHub Pages.
- [ ] إنشاء Git tag مطابق للرقم، مثل `v1.2.0`، وربطه بصفحة GitHub Release.
- [ ] إضافة ملخص واضح للتغييرات المهمة وملاحظات الترقية.

لا تعتبر إنشاء tag أو GitHub Release بديلاً عن نجاح النشر والتحقق من الموقع.

## 6. سياسة التوافق والنشر

- GitHub Pages هي منصة النشر المعتمدة حصراً.
- لا تُغيّر إعدادات النشر أو تضف مزوداً آخر دون موافقة صريحة.
- حافظ على روابط المقالات الحالية وslug ما أمكن؛ وأي تغيير ضروري يحتاج تحويل 301 موثقاً واختباراً.
- لا تُعدّل الملفات المولّدة يدوياً؛ حدّث المصدر ثم أعد التوليد.
- لا تدّع نجاح النشر قبل ظهور نتيجة GitHub Actions الناجحة والتحقق من الموقع.

## 7. المسؤولية عن السجل

يحدّث صاحب التغيير قسم Unreleased في نفس Pull Request. وتتم مراجعة اكتمال CHANGELOG.md ضمن مراجعة PR قبل الدمج. عند إصدار نسخة، تُراجع البنود وتُنقل إلى قسم الإصدار المؤرخ.
