نشر موقع HTML وCSS وJavaScript على GitHub Pages خطوة بخطوة

دليل عملي لنشر موقع ثابت على GitHub Pages، تنظيم الملفات، ضبط المسارات، إضافة sitemap وrobots وتحسين قابلية الفهرسة.

ابدأ بفهم Git قبل النشر

إذا كنت لا تزال في بداية استخدام Git وGitHub، فاطّلع أولًا على دليل Git وGitHub للمبتدئين لفهم المستودع والـcommit والـbranch ورفع التغييرات. هذا المقال يركز هنا على خطوة النشر والاستضافة بعد تجهيز المشروع.

\n

هيكل مشروع مناسب

اجعل index.html نقطة الدخول الرئيسية، وضع المقالات في articles والصفحات الثابتة في pages والموارد مثل الصور وملفات CSS وJavaScript في assets. يسهل هذا التقسيم العثور على الملفات وصيانة المشروع لاحقًا.

المسارات النسبية

اختبر المسارات من الصفحة الرئيسية ومن صفحات المقالات أيضًا. فعلى سبيل المثال، تحتاج صفحة داخل articles عادةً إلى ../assets للوصول إلى الملفات المشتركة الموجودة في مجلد assets.

GitHub Pages

بعد رفع ملفات المشروع إلى المستودع، افتح إعدادات Pages وحدد مصدر النشر المناسب. وعندما يصبح الموقع متاحًا، افتح عنوان HTTPS النهائي وتأكد من أن الصفحات والموارد تُحمّل كما ينبغي.

SEO الفني

جهّز لكل مقال عنوانًا ووصفًا للبحث ورابط canonical وبيانات Open Graph وبيانات منظمة دقيقة. أنشئ كذلك sitemap.xml وrobots.txt، وتأكد من أن جميع هذه الإشارات تطابق المحتوى المنشور فعلًا.

الصور والسرعة

اختر أبعاد الصور بما يناسب موضع عرضها، وفعّل lazy loading للصور التي لا تظهر فور فتح الصفحة، وتخلّص من الملفات غير المستخدمة. ثم قِس الأداء بأدوات الاختبار بدل الاعتماد على تقديرات غير مؤكدة.

الخلاصة

يمكن للموقع الثابت أن يقدّم أداءً جيدًا ويسهل فهرسته عندما تكون بنية HTML منظمة، والمسارات سليمة، ويحتوي كل صفحة على محتوى مفيد.

قائمة تحقق بعد النشر

  1. افتح الصفحة الرئيسية وصفحة داخلية مباشرة عبر HTTPS.
  2. افحص الصور وCSS وJavaScript وتأكد من عدم وجود أخطاء 404.
  3. تحقق من أن canonical يشير إلى النطاق المعتمد، وأن sitemap يحتوي روابط عامة صحيحة.
  4. اختبر القائمة والروابط ونموذج الاتصال على الهاتف.
  5. افتح الموقع في نافذة خاصة للتأكد من أن النتيجة ليست نسخة مخزنة مؤقتًا.

تجنّب أخطاء المسارات

في GitHub Pages لمشروع داخل مسار مثل /project/ قد يشير المسار المطلق /assets/ إلى جذر النطاق بدل مجلد المشروع. اختبر الروابط من الصفحة الرئيسية ومن مجلد المقالات. راجع وثائق GitHub Pages الرسمية لإعدادات المصدر والنشر.

قائمة تحقق للنشر على GitHub Pages

تحقق من مصدر النشر والفرع والمجلد المحدد في إعدادات المستودع، ثم راجع سجل النشر إذا لم يظهر التحديث. في المواقع الثابتة، أكثر الأخطاء شيوعًا هي المسارات المطلقة غير المناسبة، وحالة الأحرف في أسماء الملفات، والروابط التي تعمل محليًا فقط.

  • اختبر صفحة البداية وصفحات المقالات مباشرة بعد النشر.
  • افحص الصور وCSS وJavaScript في أدوات المطور بحثًا عن 404.
  • تحقق من canonical وsitemap وrobots.txt لتطابق النطاق المنشور.
  • تأكد من أن إعدادات البناء لا تستبعد مجلد المحتوى.

إذا كان الموقع يُنشر عبر سير عمل آلي، راجع حالة المهمة ورسائل الخطأ قبل إعادة تشغيلها؛ تعديل إعدادات عشوائيًا قد يخفي السبب الحقيقي.

قائمة فحص النشر بعد دفع التغييرات

نجاح عملية الدفع إلى Git لا يثبت أن الموقع المنشور يعمل. افتح رابط Pages بعد انتهاء البناء، وجرب الصفحة الرئيسية وصفحات المقالات والموارد الثابتة. عند النشر من مستودع مشروع، انتبه إلى أن المسار قد يتضمن اسم المستودع، لذلك قد تفشل الروابط المطلقة التي تبدأ من الجذر إذا لم تكن مضبوطة للمضيف.

  • راجع حالة البناء وسجلات النشر عند ظهور خطأ.
  • اختبر الروابط والصور وملفات CSS وJavaScript.
  • افتح صفحة داخلية مباشرة في تبويب جديد.
  • تحقق من إعداد HTTPS والنطاق المخصص عند استخدامه.
  • احتفظ بطريقة تراجع إلى commit معروف عند حدوث مشكلة.

بعد النشر، اختبر نسخة الموقع الفعلية بدل الاكتفاء بالمعاينة المحلية؛ اختلاف المسارات وإعدادات البناء من أكثر أسباب الأعطال شيوعًا.

قائمة تحقق لنشر موقع ثابت بأمان

قبل النشر، افصل بين الملفات المصدرية والنسخة التي تريد إتاحتها للجمهور، وتأكد من أن الفرع أو المجلد المختار في إعدادات Pages هو الصحيح. لا تضع مفاتيح سرية أو ملفات بيئة محلية في مستودع عام، لأن HTML وJavaScript اللذين يصلان إلى المتصفح لا يمكنهما حماية أسرار الخادم.

المسارات النسبية والنشر تحت مسار فرعي

قد يختلف عنوان الموقع في GitHub Pages عن نطاق مخصص أو عن خادم محلي. اختبر روابط تبدأ من الجذر بعناية، وتأكد من أن المسار يشير إلى جذر النشر الفعلي. انتبه إلى حالة الأحرف في أسماء الملفات، لأن اختلافًا صغيرًا قد يعمل على جهاز ولا يعمل على الخادم.

النطاق المخصص وHTTPS

عند ربط نطاق مخصص، تحقق من إعدادات DNS المطلوبة من وثائق GitHub الرسمية، ولا تنسخ قيمًا من مشروع آخر. انتظر حتى تنتهي عملية التحقق وإصدار الشهادة، ثم اختبر الوصول عبر HTTPS والروابط canonical. لا تغيّر DNS أو CNAME لمجرد معالجة مشكلة محتوى أو رابط داخلي.

التحقق بعد النشر

  1. افتح الصفحة الرئيسية وصفحتين عميقتين مباشرة.
  2. اختبر الصور والخطوط وملفات CSS وJavaScript من أدوات الشبكة.
  3. افحص التنقل على الهاتف، والنماذج والروابط الخارجية.
  4. راجع metadata والمعاينة الاجتماعية عند مشاركة الرابط.
  5. راقب سجل البناء والتنبيهات، واحتفظ بطريقة تراجع واضحة.

راجع دليل البدء في GitHub Pages وتوثيق النطاق المخصص. اتبع القيم الخاصة بمستودعك ولا تغيّر إعدادات النطاق دون مراجعة السبب والنتيجة.

تشخيص أكثر أخطاء النشر شيوعًا في GitHub Pages

إذا نجح البناء لكن الصفحة المنشورة لا تعمل، ابدأ بتحديد هل المشكلة في مسار النشر أم في الملفات أم في النطاق. افتح سجل البناء، وتحقق من المجلد الذي يتم نشره، ثم افحص طلبات الشبكة لمعرفة إن كانت الصفحة أو ملفات CSS والصور تعيد 404.

صفحة رئيسية تعمل وروابط عميقة تفشل

قد تشير الروابط إلى جذر نطاق مختلف عن المسار الذي ينشر فيه المشروع. اختبر عنوان صفحة عميقة مباشرة، وراجع المسارات النسبية والمطلقة. لا تغير كل الروابط إلى مسارات مطلقة دون فهم بنية النشر.

النطاق وHTTPS

إذا كان النطاق المخصص لا يعمل، تحقق من إعدادات GitHub Pages وDNS وفق الوثائق الحالية. لا تنسخ سجلات DNS من مشروع آخر ولا تعدل إعدادات النطاق أثناء معالجة خطأ محتوى. بعد اكتمال الإعداد، اختبر الوصول عبر HTTPS وتأكد من أن canonical والروابط تشير إلى النطاق الصحيح.

إجراء تراجع عند النشر الخاطئ

احتفظ بفرع أو commit معروف السلامة، وافصل تغييرات المحتوى عن تغييرات الإعدادات. إذا أحدث نشر جديد مشكلة، قارن الملفات التي تغيرت وتراجع عن التغيير المسبب بدل تعديل إعدادات متعددة عشوائيًا. وثّق الحل حتى لا تتكرر المشكلة عند التحديث القادم.
